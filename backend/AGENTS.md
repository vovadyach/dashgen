# Backend

Node.js 26 + Fastify, in TypeScript. Takes a question, and the agent answers it with a chart, on the model that `AI_MODEL` names: Gemini or Claude.

- Code in `src/`, tests in `test/`. Node runs the `.ts` files directly, so there's no build step: `tsc` only checks types.
- Run it with `npm run dev` from the repo root: port 3000, restarts on changes, reads `backend/.env`. API docs at http://localhost:3000/docs.
- It's a package in the repo's npm workspace: install from the root with `make install`. In this folder, `npm test` and `npm run typecheck` check just the backend. Formatting and linting run from the root (`npm run format`, `npm run lint`), or all of it with `make check`.

## Conventions

- Settings are read in `loadConfig` in `config.ts`, through a Zod schema. A new setting goes there and into `.env.example`. Secrets are wrapped in `Secret`, so they never reach logs.
- The agent loop talks to the model through the `Model` interface (`agent/types.ts`), with one adapter per provider: `gemini.ts` and `claude.ts`. `AI_MODEL` picks a model from `MODELS` in `config.ts`, which holds each one's provider and prices, and `createModel` (`agent/models.ts`) builds it. A new model of a provider DashGen has goes in `MODELS`, with its prices, and in `model_providers` in `infra/aws/session/secrets.tf`, which a test keeps the same; a new provider needs an adapter, tests like `gemini.test.ts`, its key in the session stack (`secrets.tf`, `variables.tf` and `make aws-up`'s check), and an ADR ([ADR-0016](../docs/decisions/0016-ai-model-setting.md)).
- Each module keeps its tables in its own `schema.ts` (`metrics/`, `runs/`), and `db.ts` opens the connection pool and runs the migrations.
- IDs are UUIDv7 ([ADR-0009](../docs/decisions/0009-uuidv7-ids.md)): `randomUUIDv7()` from `node:crypto` in code, and `uuidv7()` as a Postgres column default. Never v4 (`randomUUID()`, `gen_random_uuid()`, Drizzle's `defaultRandom()`).
- The image (`backend/Dockerfile`) gets only what the root `.dockerignore` lists. A file or folder the backend needs at run time goes in that list, and in the Dockerfile's `COPY` lines, or the container won't find it.
- DynamoDB is reached only through `dynamo.ts`. `createDynamo` is for DynamoDB Local, with fake keys, so no run on a developer's machine can reach a real AWS account. `createAwsDynamo` is for AWS's own, and only `DYNAMODB_REGION`, which just the backend's task definition sets, picks it (`loadDynamoTarget`). It signs with the ECS task's role, from `ecsCredentials`, which asks ECS itself, within 1 second, and asks again after a failure: the SDK's own lookup can wait forever on a reply that stalls. Outside an ECS task it fails, so it never signs with a developer's own credentials. Every send goes through `withDeadline`, which ends it 2 seconds after it starts, the credential lookup included, since the client's own timeout ends once a reply's headers arrive.
- Inside a transaction, use `tx`, never `db`, and `await` each query in turn (`seedMetrics`). A transaction is one connection, so `Promise.all` there runs nothing in parallel, and after a failure the rest of its queries fail too. Outside transactions, `Promise.all` does run independent reads in parallel, on separate pool connections (`listServices`).
- A database call that's safe to repeat goes through `retryOnce` in `db.ts`: one more try after a failure that can pass, like a lost connection or a timeout (`isRetryable`), and none once its `signal` aborts, as at a run's deadline. A read is safe to repeat. An insert is when it has a stable ID and does nothing on a conflict (`saveRun`). Wrap a whole transaction, never one query inside it, since after a failure the rest of its queries fail too. The model's retry is in the agent loop instead, because each request counts toward the run's limit.
- A module's own Zod schemas and their types go in `types.ts`, checks beyond a schema's shape in `validation.ts`, and small general helpers, like `distinct`, in `helpers.ts`, so the other files only do the work (`agent/`). Schemas that another package also needs go in `packages/contracts` instead.
- Modules, `app.ts` and `server.ts` import a module only through its `index.ts` ([ADR-0005](../docs/decisions/0005-one-backend.md)); tests and scripts may reach inside. A helper that a second module needs moves to `src/shared/`. The app's foundations (`config.ts`, `db.ts`, `dynamo.ts`, `logger.ts`, `errors.ts`) stay at the top of `src/`.
- Modules take what they need as parameters, like `createMetrics(db, { now, log })`, so tests can pass a test database, a fixed clock and their own logger. Logging levels and the "log once, where it's handled" rule are in `src/logger.ts`.
- `buildApp(config, { runs })` builds the app, so each test can pass its own config, and fakes for the model, the database and the daily cap through `runs` (`startApp` does). Nothing else reads the environment.
- Each route declares Zod schemas for its body and responses. They validate requests, type the handler, check replies and generate the docs at `/docs`. A schema that a client also needs lives in `packages/contracts` and is imported from `@dashgen/contracts`.
- Errors are thrown as `ApiError(status, code, message)`, so clients get `{"error": {"code": "...", "message": "..."}}`. The message must be safe to show visitors. The code is an `ApiErrorCode` from `@dashgen/contracts`, so a new one goes there first.
- Logging is Pino, through Fastify: a short, stable message naming the event, with context as fields (`{ tool, args, ms }`), never secrets or the values in SQL. `LOG_LEVEL=debug` adds every SQL statement, and `npm run dev` shows readable lines through `pino-pretty`. Each line is JSON, with its level as a word, like `"error"`. A request's lines carry its ID as `reqId`, and a run's lines its `runId` too, which is how CloudWatch finds them on AWS ([deploy runbook](../docs/runbooks/deploy.md#read-the-backends-logs)). Expected errors throw with a reason; only the central handler logs unexpected ones, once.
- Per-route behavior, like the rate limit, goes in the route's options: `config: { rateLimit: ... }`.
- Only TypeScript that Node can strip: no `enum`, no parameter properties, and relative imports end in `.ts`. The `erasableSyntaxOnly` setting enforces it.
- No `any`, and ESLint's type-aware rules must pass, including the one against promises nobody awaits.
- `src/mcp/` gives MCP clients some of the agent's tools, through `createTools`, so their names, schemas and checks stay one set ([ADR-0022](../docs/decisions/0022-mcp-server.md)). It answers `tools/list` and `tools/call` on the SDK's low-level server, not through `registerTool`, so every call reaches the agent's tool, which checks and counts it, and each call's abort signal reaches its reads. A tool's `ToolError` goes back to the client's model, and any other failure is logged, with the client getting no details. An unknown tool is a protocol error instead, as MCP's spec asks. `src/scripts/mcp.ts` serves them over stdio, where stdout carries MCP's messages: clients start it with `node`, never npm, and it logs through `consoleLogger(level, { stderr: true })`.
- `evals/` holds the agent's evals ([ADR-0018](../docs/decisions/0018-agent-evals.md)): the cases in `cases.ts`, with their rules in `cases.md`, the grader in `grade.ts`, and the loop in `runner.ts`, which `run.ts` runs as `npm run eval`, as CI does on pull requests that change the agent ([ADR-0019](../docs/decisions/0019-evals-in-ci.md)). A new case gets its right answer written by hand, and its row in `cases.md`. The grader's and the loop's own tests run on the fake model, in `test/integration/evals/`, so `make check` runs them for free.
- Tests use `node:test`, split by what they need:
  - `test/unit/`: pure logic, with no database or network. `npm run test:unit` runs them without Docker.
  - `test/integration/`: real parts together. Routes go through `app.inject()` (`startApp` in `test/helpers/app.ts`), and Postgres through `createTestDb()` (`test/helpers/db.ts`), which gives each file its own migrated database on the test Postgres that `make check` starts (or on `TEST_DATABASE_URL`, which must be Postgres 18 or later). DynamoDB goes through `createTestTable()` (`test/helpers/dynamo.ts`): a table per file, on the test DynamoDB Local (or on `TEST_DYNAMODB_ENDPOINT`).
  - Inside each, a subfolder per module once a module has several test files. Tests never call Gemini or Claude: they use `fakeModel` from `test/helpers/model.ts`, and the adapters' own tests fake the provider's API with `fakeFetch` (`test/helpers/fetch.ts`).
- Tests are grouped with `describe`, named for what they test: a function (`runAgent`) or a part of the app (`HTTP API`), with a `describe` inside for each group when there are many (`limits`, `POST /api/ask`). Each `it` reads on from its `describe`: `describe("query_metrics")`, then `it("fills in the default range of 7 days")`. The test report shows no file names, so the groups show where each test lives.
- Test files hold the tests, their `before`/`after` hooks, test case tables and small helpers for that file, like `ask()`. Test data goes in `test/fixtures/` (`QUESTION`, `CATALOG`, `VALID_ENV`), unless only one test uses it. Shared functions go in `test/helpers/`: fakes (`fakeModel`), builders (`reply()`), setup (`startApp()`) and checks (`assertRecentUuidV7()`).
