# Roadmap

DashGen is built in nine steps. Each one ends with something that works end to end.
The reasoning behind bigger choices lives in [decisions](decisions/).

- Every step ships with its tests.
- **Product first:** a thin slice from question to chart works early (step 3), and every later step makes it safer, deployed, measured or nicer. The guardrails come before the first deploy, because the deployed demo is public.
- The AWS backend runs only while it's being worked on, and `terraform destroy` removes it after each session. Only a small stack stays on, so the link and the page keep working in between ([ADR-0003](decisions/0003-cloudfront-front-door.md)).
- `make` runs repo-wide and infrastructure commands (`make check`, `make db`, and later `make up` and `make down`). npm scripts run the TypeScript packages.

## 1. Foundation

- [x] Metrics service in Go with hardcoded data
- [x] Move the gateway from Express to Fastify and TypeScript ([ADR-0001](decisions/0001-node-gateway.md)), renaming `POST /chat` to `POST /ask` ([ADR-0002](decisions/0002-question-box.md))
- [x] npm workspaces: shared TypeScript tooling, and a `contracts` package for API schemas ([ADR-0004](decisions/0004-npm-workspaces.md))
- [x] Tests for the metrics service and the gateway
- [x] `scripts/check.sh`: one command that runs every formatter, linter, type checker and test
- [x] CI on GitHub Actions that runs `scripts/check.sh`
- [x] Claude Code setup: a `CLAUDE.md` per service, permissions, format and stop hooks, `fix-issue` and `adr` skills
- [x] `docs/architecture.md`: how the services fit together
- [x] README and Makefile brought up to date
- [x] Design for one TypeScript backend, with Drizzle and tRPC ([ADR-0005](decisions/0005-one-backend.md), [ADR-0006](decisions/0006-drizzle.md), [ADR-0007](decisions/0007-trpc.md))

**Done when:** `scripts/check.sh` passes locally and in CI, and failing checks send Claude back to fix them before it finishes.

## 2. Data: one backend with Postgres and Drizzle

- [x] `gateway/` renamed to `backend/` ([design](design.md#inside-the-backend))
- [x] The Go metrics service removed, along with `make metrics` and Go in CI and `scripts/check.sh`
- [x] One Postgres database and user, `dashgen`, replacing the two from Docker Compose ([design](design.md#one-database))
- [ ] Drizzle schema for `services`, `metrics` and `points` ([design](design.md#the-metrics-tables)), and `runs` ([design](design.md#the-runs-table))
- [ ] Migrations generated by `drizzle-kit` and committed as SQL
- [ ] Seed: 30 days of hourly data ending today, from a fixed random seed, in one transaction
- [ ] The `metrics` module's `listServices()` and `query()`: up to 30 days, hourly or daily buckets, rollups and a summary ([design](design.md#the-metrics-module))
- [ ] Tests against a real Postgres, locally and in CI
- [ ] ADR: why Postgres, and what changes at scale. It replaces design.md's [Why Postgres](design.md#why-postgres), which then links to it

**Done when:** `make db` starts Postgres, the migrations and the seed run, and tests show `metrics.query()` returning the design's example from the seeded data.

## 3. First slice: question to chart

- [ ] Chart format first: what the backend sends and the page draws ([design](design.md#the-frontends-api))
- [ ] [Tools](design.md#the-agents-tools): `list_services`, `query_metrics` and `create_chart`, each with a description that also says what it doesn't handle
- [ ] Hand-written Gemini function-calling loop that records each step. The model sits behind an interface the loop receives, so tests use a scripted fake model and never call Gemini
- [ ] The [per-run limits](design.md#the-daily-cap) from the first live call: 6 model calls, the token budgets, a timeout on each call and 25 seconds per run
- [ ] The backend builds each chart from the query results `create_chart` names
- [ ] Read-only tools that accept only known service and metric names
- [ ] Tool arguments and the final chart validated against their schemas
- [ ] The question schema in `contracts`: 1 to 300 characters after trimming
- [ ] tRPC router: the `ask` mutation starts a run and returns its ID, and the `run` subscription streams its events over SSE, replaying missed ones on reconnect ([ADR-0007](decisions/0007-trpc.md))
- [ ] Errors carry our codes through tRPC's error formatter; the per-IP limit counts each `ask`, not each HTTP request
- [ ] Each run saved to `runs`
- [ ] React + Vite + Tailwind + Recharts, with tRPC and TanStack Query: question box, steps panel, chart
- [ ] Vite's dev server forwards `/api` to the backend, so the app calls the same paths locally and on AWS
- [ ] Component tests with Vitest, frontend checks in `scripts/check.sh`, and a `frontend/CLAUDE.md`

**Done when:** locally, asking "Show errors for payments-service this week" in the browser streams the steps and draws the chart.

## 4. Guardrails and cost

- [ ] `clarify` with clickable choices when the question is vague, and `decline` with example questions when it's off-topic
- [ ] Errors classified as retryable or not; retries use exponential backoff with jitter
- [ ] [Daily cap](design.md#the-daily-cap) of 150 questions, counted in DynamoDB, with DynamoDB Local in Docker Compose
- [ ] A friendly message when the daily cap is hit, with a link to the demo video
- [ ] A $20 monthly spend cap on the Gemini project, noted in the runbook
- [ ] Model name in config
- [ ] Tokens, cost and latency recorded for every run, and cost per day and per question read from `runs`

**Done when:** a vague question gets a clarifying question back, at the daily cap the backend stops calling Gemini, and every run's cost is recorded.

## 5. Docker and AWS

- [ ] Dockerfile for the backend, and Docker Compose that starts Postgres and DynamoDB Local, runs the migrations and seed, then starts the backend
- [ ] `HOST` and `PORT` settings, so the backend listens inside a container
- [ ] AWS account with MFA and budget alerts at $10, $25 and $50
- [ ] All infrastructure defined in Terraform: the always-on and session stacks from the [AWS design](design.md#on-aws)
- [ ] `terraform destroy` finishes cleanly: secrets deleted with no recovery window, RDS without a final snapshot, ECR repositories deleted with their images
- [ ] No database backups: every deploy reseeds the data, and the `runs` history starts over
- [ ] `terraform-reviewer` subagent (read-only) that reads `terraform plan` and reports only what would be deleted or replaced
- [ ] VPC with public and private subnets, a NAT gateway, and a gateway endpoint for DynamoDB
- [ ] The backend's routes under `/api` (`/api/trpc`, `/api/health`)
- [ ] CloudFront as the only address visitors use, with the `/api/*` settings, headers and timeouts from [ADR-0003](decisions/0003-cloudfront-front-door.md), forwarding query strings for tRPC
- [ ] A CloudFront Function and key-value store that send `/api/*` to the running session, or answer 503 `{"status": "offline"}` between sessions, and a `make down` that drains the API before `terraform destroy`
- [ ] The backend on ECS Fargate behind a load balancer that accepts only our CloudFront: exactly one task, since the rate limit and run events live in its memory, and deploys that stop the old task first
- [ ] Postgres on RDS (db.t4g.micro) in private subnets, with migrations and the seed run as a one-off ECS task
- [ ] Database password and the Gemini key in AWS Secrets Manager, passed to the container by ECS
- [ ] Structured JSON logs with a request ID, collected in CloudWatch
- [ ] GitHub Actions builds the image and deploys it, signing in to AWS with OIDC instead of stored keys
- [ ] The React app deployed to the always-on S3 bucket behind CloudFront, with an offline banner when `/api/health` doesn't answer within 3 seconds
- [ ] Rate limiting keyed on the visitor's IP from `CloudFront-Viewer-Address`, with a test that a forged `X-Forwarded-For` doesn't change it
- [ ] Deploy runbook: `docs/runbooks/deploy.md`

**Done when:**

- `docker compose up` runs everything locally.
- `terraform apply` builds the stack from nothing, GitHub Actions deploys to it, and `terraform destroy` removes everything except the small stack that stays.
- Through CloudFront, the example question works with its steps streaming, and after `make down` the page shows the offline banner.
- A request sent straight to the load balancer, skipping CloudFront, doesn't reach the backend.

## 6. Evals

- [ ] 20–30 test questions, each with the expected tool calls, chart type and chart data: values, dates and units
- [ ] Ambiguous questions where the right answer is a clarifying question
- [ ] Scored for accuracy; runs from the command line and in CI, calling the agent loop directly
- [ ] `eval-runner` subagent on Haiku that runs the evals and returns only the score and the failures
- [ ] Model routing: a cheaper model first, a stronger one when its answer fails validation, kept only if evals show it saves money without losing accuracy

**Done when:** the README reports the agent's eval accuracy.

## 7. Frontend polish

- [ ] Example questions under the box for first-time visitors
- [ ] Pin charts to a dashboard, saved in the browser with their data, so they still draw while the backend is offline
- [ ] A note under the question box says questions are saved
- [ ] Works on a phone
- [ ] Invisible bot check (Cloudflare Turnstile)

**Done when:** a first-time visitor on a phone can pick an example, pin the chart, and still see it after the backend goes offline.

## 8. MCP server

- [ ] MCP server that exposes DashGen's tools to any MCP client
- [ ] Demo from Claude Code

**Done when:** Claude Code answers a metrics question through DashGen's MCP server.

## 9. Demo and write-up

- [ ] Full stack redeployed
- [ ] Demo video
- [ ] README for engineers: architecture, real numbers (eval accuracy, cost per question, latency) and a "One thing I got wrong" section

**Done when:** the README has the demo video and real numbers, and the stack is destroyed.
